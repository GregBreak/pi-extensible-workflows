## Live browser spike and maintenance inventory

`trajectory-browser.test.ts` contains two reproducible browser probes using the pinned template and existing Node/CDP harness (no npm dependency): the unmodified Finder and a localized in-memory Finder refresh patch. Both run in `sandbox="allow-scripts"` only (no `allow-same-origin`) with CSP denying connections/object/base/form and allowing inline scripts/styles plus embedded data images/fonts. The test-only bridge transfers a fixed-nonce `MessagePort` without run data; this is not the production handshake or three-external-asset CSP proof. The tests were built and passed in real Chrome using the dependency-equipped scratch checkout under `.tmp/archify/baseline`.

Observed in that browser:

- The pinned page initializes a static SVG shell with **0 graph nodes** and Finder count 0; it is not a live JSON graph API. The fixture appends, changes a status attribute on, and removes a new SVG node through the private port; camera state is stable before explicit selection. Local resize and three iframe dispose/reopen cycles work. The server observed only the parent and viewer document requests and CSP denies connections; network listeners start after navigation, so this is not a complete cold-load external-network audit.
- The original spike in `2ebcb98` removed the node BEFORE searching/selecting it. Its passing result did not establish the claimed live-node failure. Recovery now asserts `nodePresent === true` at search/selection time, then tests removal separately. The corrected unmodified viewer genuinely reports count 0, no result and failed selection while the node remains attached, consistent with the documented captured Finder index.
- A localized patch now demonstrates that this Finder limitation is repairable: `finder-live.patch.json` changes three uniquely matched anchors in one capability, extracts its existing item collection into a callable function, adds explicit `refresh()`, and makes `count` reflect the refreshed array. It does not reinitialize the viewer, add listeners, change the pinned input or replace Archify search/focus with a custom implementation.
- In the patched real-browser test, after insertion and explicit refresh: Finder count is 1, search returns the node, `select()` returns true, and **`Archify.focus.active()` equals the inserted ID**. After removal and refresh, count/search are 0 and selection returns false. Both tests retain the opaque sandbox, local resize and three dispose/reopen cycles. Status mutation is an SVG-attribute observation only; it is not a full live status-renderer proof.
- Patch measurements: pinned input **774,866 B**, patched in-memory input **775,040 B**, net addition **174 B**; the checked-in patch recipe is **776 B**, with **3 anchor sites in 1 upstream capability**. Hash/unique-anchor checks fail closed on input drift. This is a Finder feasibility patch, not the final vendor-source update strategy or full graph lifecycle implementation.
- Camera state is checked before explicit Finder selection; a successful selection is allowed to move the camera. Removal of a focused node, geometry changes, relationships, initial nonempty graphs, external three-asset CSP, 50-cycle/heap behavior and the full profiled artifact remain to be demonstrated. The node fixture has actual rectangle geometry and focusability. Optional advanced capabilities are not yet profiled. Production adapter/renderer and final package/HTTP delta remain unimplemented/unmeasured.

The corrected evidence does **not** establish either a full GO or a maintainability NO-GO. It disproves the assumption that the Finder issue alone requires an invasive fork. Complete the remaining bounded E0 adaptation/measurement before E1–E4; do not restart successful baseline installation or measurements just to repeat this correction. A no-go must identify a demonstrated hard blocker or concrete unacceptable patch cost, not merely an absent upstream API.
